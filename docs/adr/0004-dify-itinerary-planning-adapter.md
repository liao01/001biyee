# Dify 作为可替换的行程规划适配器

状态：已决定。结构化行程规划以 MySQL 保存规划请求、修订建议、建议操作和建议确认等领域状态，并通过正式行程命令应用已确认的变更；Dify 只作为 `ItineraryPlannerGateway` 的首个可替换生成适配器，通过已发布 Workflow 使用外挂知识库。这样可以复用现有 Dify 运维能力，同时保证模型、工作流和供应商被替换时，正式旅行行程和用户决定不需要迁移。

## 考虑过的方案

- 不让 Dify 直接写旅行行程。Dify 的运行记录、工作流配置和知识检索结果不具备行程权限、版本、幂等和事务语义；允许直接写入会绕过行程命令边界，并形成 MySQL 之外的第二业务事实源。
- 不把现有 LangChain4j 能力同时建设成第二条正式规划路径。双路径会复制提示词、输出契约、重试与失败分类，并让同一规划请求因路由不同产生两套运维口径；未来替换适配器时应在同一网关边界内完成，而不是长期并行两个正式入口。
- 不读取 Dify 自用的 PostgreSQL、Redis、向量库或数据卷。平台只消费 Workflow API 的版本化输出，知识库和模型编排仍由 Dify 自己管理。

## 结果

生成调用不能持有行程仓储或正式写接口；Dify 输出必须先转换为供应商无关的修订建议并由后端确定性校验。拒绝、失败和未确认建议不改变旅行行程，确认只能通过 `ItineraryApplicationService` 的原子修订命令。更换 Dify 时需实现相同网关契约并迁移运行配置，但不迁移规划领域数据。
