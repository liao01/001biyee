# 模块化单体优先，按明确触发条件拆分服务

## 状态

已决定。

## 背景

系统将从以帖子为主的旅游分享平台扩展为以旅行行程为核心的智能旅行平台，包含 AI 规划、地图、协作、费用、执行记录、社区、推荐和内容治理等业务模块。系统近期由个人持续开发，并首先部署在一台云服务器上。

立即拆分微服务可以提供独立部署边界，但会同步引入服务发现、跨服务一致性、调用治理、分布式追踪、更多部署单元和本地开发成本。继续维持按 Controller、Service、Mapper 的全局分层则会让新增业务共享内部数据结构，难以形成稳定边界。

## 决定

后端首先采用一个 Spring Boot 部署单元，并按账户、行程、AI、协作、执行、费用、社区、推荐和治理等领域组织为模块化单体。

- 模块只能通过正式应用接口或领域事件协作。
- 其他模块不得直接依赖某个模块的内部 Mapper、数据库对象或实现类。
- 同步查询和命令使用模块接口；通知、索引、统计等副作用使用事务提交后的领域事件。
- MySQL 仍是正式业务数据的唯一事实源，搜索和缓存可重建。
- 只有出现独立扩缩容、故障隔离或团队所有权需求时，才将某个模块拆为独立服务。

AI、搜索和通知是可能最先满足拆分条件的模块，但本决定不预先承诺必须拆分。

## 结果

### 正面结果

- 保持单服务器部署、事务处理和本地调试简单。
- 通过稳定模块接口展示清晰架构，而不承担当前没有收益的分布式成本。
- 模块边界为未来按需拆分服务提供迁移接缝。

### 代价

- 需要用架构测试和代码审查持续阻止跨模块内部依赖。
- 所有模块共享一个后端发布节奏，不能立即独立部署。
- 若模块边界设计不严谨，单一部署单元仍可能退化为普通单体。

### 后续检查

每次考虑拆分服务时，必须给出可验证的触发证据：独立扩缩容需求、故障隔离需求或明确的团队所有权边界。仅以模块数量或技术展示为理由不得拆分。
