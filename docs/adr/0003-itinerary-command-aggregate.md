# 旅行行程采用规范化聚合与命令边界

状态：已决定。旅行行程是后续智能规划、协作、费用和执行能力共同引用的核心对象，因此采用 MySQL 规范化聚合保存行程、目的地、日程日和条目，并由应用服务的命令边界统一处理事务、幂等与乐观版本；命令最小结果单独持久化。该决定延续 [ADR-0002](0002-modular-monolith-first.md) 的模块化单体边界，模块外只调用正式应用接口或消费事务提交后的领域事件。

## 考虑过的方案

- 通用 CRUD 会把所属关系、版本递增、日期收缩、时间冲突和排序规则分散到 Controller 或调用方，无法保证一次业务变更的原子性，因此不采用。
- 把完整行程保存为 JSON blob 可以较快增加字段，但会弱化外键、索引、局部约束与可审计迁移，并形成与关系数据竞争的第二事实源，因此不采用。
- 当前不使用事件溯源；#17 需要可重放命令结果而非以全部历史事件重建聚合，事件存储的复杂度没有相应收益。

## 结果

所有行程写入必须通过命令边界，在一个事务中验证负责人权限、期望版本和领域规则，并写入命令结果。读取投影和前端状态可从规范化表重建，不得反向成为事实源。#18–#32 的 AI 建议、成员协作、费用、预订参考、执行记录、社区、推荐与治理分别保留自己的模块事实；它们通过行程 ID 和正式接口/事件关联，不向核心表追加通用扩展 JSON。若未来出现独立扩缩容、故障隔离或团队所有权证据，再按 ADR-0002 评估拆分服务。
